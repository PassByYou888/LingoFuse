## Chapter 1 Reading guide

### 1.1 What this document solves

This document is the **standalone manual** for the LingoFuse Rust binding. After reading it you can:

- bring the `lingofuse` crate into your own Rust project
- write LingoFuse servers and callers in Rust
- target a peer with the three addressing modes (App name / UID / P2PName)
- write non-blocking code with the closure-based async API
- configure runtime parameters with the typed option API
- interoperate with the Pascal / Python / C++ / C# / JavaScript sides
- run and understand the binding's test system
- judge which of the work that used to need POC validation the Rust binding has replaced

### 1.2 Reading paths

| Your goal | Reading path |
|---------|----------|
| first time, just want it to run | Chapter 2 → §3.1 |
| deep understanding of the API | all of Chapter 3 |
| only the three addressing modes | §3.2.3 → §3.3.4 |

### 1.3 Terminology

| Term | Meaning |
|------|------|
| **native library** | LingoFuse's C ABI dynamic library (`LingoFuse64.dll` and the like) |
| **C ABI** | the 59 C functions the native library exports |
| **data handle** | `DataHandle`, a byte buffer tagged with an API name |
| **application handle** | `AppHandle`, a named container for a group of related APIs |
| **UID** | a 32-byte session identifier, generated by the client after a successful `TunnelLink`, and changing on reconnect |
| **P2PName** | a user-defined group name; the server load-balances by group |
| **mesh** | the C4 service mesh, providing discovery, routing and load balancing |
| **side data** | metadata the sender injects automatically into the head of the request payload (`FromUID` / `FromP2PName`), readable only on the receiving side's `input` handle in a callback |
| **async call** | the callback-based call family; its **handle ownership** is opposite to the synchronous family |

## Chapter 2 Library integration

### 2.1 Dependency list

The `lingofuse` crate depends on three third-party libraries:

| Dependency | Version | Purpose |
|------|------|------|
| `libloading` | 0.8 | load the native shared library at runtime |
| `serde` | 1.x | JSON serialization / deserialization (with `derive` enabled) |
| `serde_json` | 1.x | JSON encoding and decoding |

This binding **does not depend on any async runtime** (no tokio / async-std / futures). The async call module is built on `std::sync::mpsc` and closures.

### 2.2 Adding the dependency

**Option A: as a path dependency (recommended when developing in the same repository)**

In your `Cargo.toml`:

```toml
[dependencies]
lingofuse = { path = "../LingoFuse/rust" }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

**Option B: as a git dependency**

```toml
[dependencies]
lingofuse = { git = "https://github.com/PassByYou888/LingoFuse", branch = "main", subdir = "rust" }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

**Option C: use the local crate directly**

Copy the `rust/` directory into your project and turn it into a path dependency.

### 2.3 Deploying the native library

The `lingofuse` crate **loads the library at runtime** and does not link against it at build time. You need to put the native library where the Rust loader can find it.

**The required files**:

| Platform | Core library | IPC dependency |
|------|--------|----------|
| Windows 64-bit | `LingoFuse64.dll` | `z_ipc_64.dll` |
| Windows 32-bit | `LingoFuse32.dll` | `z_ipc_32.dll` |
| Linux | `liblingofuse.so` | `libz_ipc.so` |
| macOS | `liblingofuse.dylib` | `libz_ipc.dylib` |

**Where to deploy** (in loader search order):

1. the directory holding the current executable
2. the current working directory
3. the system loader search path (`PATH` / `LD_LIBRARY_PATH` / `DYLD_LIBRARY_PATH`)

**The least troublesome approach**: add the LingoFuse repository's `Binary/` directory to the system `PATH`.

Windows PowerShell:

```powershell
$env:PATH = "C:\path\to\LingoFuse\Binary;$env:PATH"
```

Linux / macOS:

```bash
export LD_LIBRARY_PATH=/path/to/LingoFuse/Binary:$LD_LIBRARY_PATH
```

### 2.4 Platform dependencies

On Windows you need the **VC++ 2015-2022 redistributable package** (it provides the C runtime dependencies of the native library).

On Linux, if you use a musl target, make sure `liblingofuse.so` is musl-ABI compatible (the native library is built against glibc by default).

### 2.5 Verifying that the library loads

Run a minimal example in your project:

```rust
use lingofuse::sys;

fn main() {
    match sys::load_library() {
        Ok(_) => println!("[OK] LingoFuse native library loaded"),
        Err(e) => eprintln!("[FAIL] {}", e),
    }
}
```

**If it prints `[OK]`, the library loaded successfully.**

If it prints `[FAIL]`, the error message lists every path that was tried; adjust the deployment location accordingly.

## Chapter 3 Usage

### 3.1 The minimal runnable example

#### 3.1.1 The server

Create `src/bin/server.rs`:

```rust
use lingofuse::app_handle::AppHandle;
use lingofuse::framework;
use lingofuse::io;
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct AddArgs {
    a: i32,
    b: i32,
}

#[derive(Serialize)]
struct AddResult {
    sum: i32,
}

fn main() -> Result<(), lingofuse::error::Error> {
    // deployment mode: do not block waiting for the mesh to become ready
    framework::set_option("Wait_Connection_ReadyOk", "False")?;
    framework::set_option("Quiet", "True")?;

    // create an application and register an API
    let app = AppHandle::new("Calculator", "a simple calculator")?;

    app.register_call("add", "add two numbers", |input, output| {
        if let Ok(args) = io::read_json::<AddArgs>(input) {
            let _ = io::write_json(output, &AddResult { sum: args.a + args.b });
        }
    })?;

    // network preparation
    framework::reset_prepare();
    framework::prepare_service("ipc:calc", "ipc:calc")?;
    framework::prepare_client("ipc:calc", Some(&app))?;
    framework::prepare_done()?;

    println!("Server ready; press Enter to exit.");
    std::io::stdin().read_line(&mut String::new()).ok();

    drop(app);
    framework::exit_main_thread();
    framework::shutdown();
    Ok(())
}
```

#### 3.1.2 The caller (synchronous)

Create `src/bin/client.rs`:

```rust
use lingofuse::data_handle::DataHandle;
use lingofuse::framework;
use lingofuse::io;
use serde::{Deserialize, Serialize};
use std::time::Duration;

#[derive(Serialize)]
struct AddArgs {
    a: i32,
    b: i32,
}

#[derive(Deserialize)]
struct AddResult {
    sum: i32,
}

fn main() -> Result<(), lingofuse::error::Error> {
    framework::set_option("Wait_Connection_ReadyOk", "False")?;
    framework::reset_prepare();
    framework::prepare_client("ipc:calc", None)?;
    framework::prepare_done()?;

    // build the request
    let mut req = DataHandle::new("add")?;
    io::write_json(&mut req, &AddArgs { a: 5, b: 7 })?;
    req.set_position(0)?;

    // retry loop: the mesh broadcast can take up to about 3 seconds to reach the local cache
    let mut response = None;
    for _ in 0..30 {
        match framework::try_call("Calculator", &req, 3000)? {
            Some(r) => {
                response = Some(r);
                break;
            }
            None => {
                req.set_position(0)?;
                std::thread::sleep(Duration::from_millis(200));
            }
        }
    }

    let mut resp = response.expect("the call did not succeed within 6 seconds");
    resp.set_position(0)?;
    let out: AddResult = io::read_json(&mut resp)?;
    println!("5 + 7 = {}", out.sum);

    drop(resp);
    drop(req);
    framework::exit_main_thread();
    framework::shutdown();
    Ok(())
}
```

#### 3.1.3 The caller (asynchronous)

The same call, rewritten with the closure-based async API:

```rust
use lingofuse::{async_call, framework, io};
use lingofuse::data_handle::DataHandle;
use serde::{Deserialize, Serialize};
use std::time::Duration;

#[derive(Serialize)]
struct AddArgs { a: i32, b: i32 }

#[derive(Deserialize, Debug)]
struct AddResult { sum: i32 }

fn main() -> Result<(), lingofuse::error::Error> {
    framework::set_option("Wait_Connection_ReadyOk", "False")?;
    framework::reset_prepare();
    framework::prepare_client("ipc:calc", None)?;
    framework::prepare_done()?;

    let mut req = DataHandle::new("add")?;
    io::write_json(&mut req, &AddArgs { a: 5, b: 7 })?;
    req.set_position(0)?;

    // submit the async request. The closure runs on a native worker thread.
    async_call::call_async("Calculator", &req, move |result| {
        match result {
            Ok(mut resp) => {
                if let Ok(out) = io::read_json::<AddResult>(&mut resp) {
                    println!("5 + 7 = {}", out.sum);
                }
            }
            Err(e) => eprintln!("async call failed: {}", e),
        }
    })?;

    // keep the process alive until the callback fires.
    std::thread::sleep(Duration::from_secs(1));
    framework::exit_main_thread();
    framework::shutdown();
    Ok(())
}
```

#### 3.1.4 Running them

```bash
# make sure the native library is on PATH / LD_LIBRARY_PATH
cargo run --bin server    # terminal 1
cargo run --bin client    # terminal 2
```

**Expected output**: `5 + 7 = 12`

### 3.2 Core concepts

#### 3.2.1 The data handle (DataHandle)

A data handle is LingoFuse's **basic primitive** — a byte buffer tagged with an API name, with a read / write cursor.

Two kinds of handle:

| Kind | Construction | Idle reclaim | When it is released |
|------|------|:--------:|----------|
| **auto-recycled** | `DataHandle::new("api")` | reclaimed by the pool scan after 10 minutes idle (scanned every 5 seconds) | `Drop` marks it deleted; the next scan actually releases it |
| **permanent** | `DataHandle::create_permanent("api")` | never auto-reclaimed | `Drop` releases it synchronously |

**The key difference**:

- auto-recycled handles: forgetting `Drop` has a safety net, but a leaked handle is possible under heavy load
- permanent handles: suited to template caching that outlives a process lifecycle; **you must `Drop` them explicitly**

**Borrowed handles**: the `input` / `output` a callback receives are **borrowed** — the native layer owns them and releases them once the function returns. **Do not** call `dispose()` on them.

#### 3.2.2 The application handle (AppHandle)

An application handle is **a named container for a group of related APIs**. It is the basic unit of network routing:

- the caller specifies `(app name, API name)`
- the mesh dispatches the call to one client that hosts that application
- app names are case-insensitive
- one client can host only one application at a time (unless `Overlap_Connection` is enabled)

#### 3.2.3 The three addressing modes

LingoFuse supports three routing keys. They are **parallel**, not mutually exclusive; the same server supports all three at once:

| Addressing | Key | Routing | Local first? | Load balanced? | Typical use |
|------|-----|---------|:----------:|:----------:|---------|
| **App name** | a UTF-8 string | exact App-name match | ✅ | ❌ | a fixed service |
| **UID** | 32 bytes of binary | locate one client by session identifier | ✅ | ❌ | target a specific client |
| **P2PName** | a UTF-8 string | load-balance by group name | ❌ | ✅ | a cluster of homogeneous services |

**The key differences**:

- **UID** is a **session-level** identifier: the client generates it after a successful `TunnelLink`, and it **changes on reconnect**. Knowing a client's UID lets you call **any API it registered** (including those registered by app name and those registered as P2P), without knowing the app name.
- **P2PName** routing **does not do a local lookup**: it is always dispatched through the server dispatcher, which owns the load-balancing state.
- **App-name** routing is **local-first**: if this process has an App of the same name and it has the target API, the call executes locally without going over the network.

Rust API naming convention: app-name addressing uses the **bare name** (e.g. `call`), UID addressing uses the `*_by_uid` suffix, and P2PName addressing uses the `*_by_p2p_name` suffix. The three modes appear **symmetrically** in the `framework` module.

#### 3.2.4 Call modes

| Mode | Rust API | Semantics | Ordering guarantee | Return value |
|------|----------|------|:--------:|:------:|
| **Call** | `framework::call` / `try_call` | request-response | — | ✅ |
| **Notify** | `framework::notify` | one-way notification | ❌ | ❌ |
| **Sequenced Notify** | `framework::sequenced_notify` | one-way notification | ✅ (FIFO within one `(app, api)` pair) | ❌ |
| **Async Call** | `async_call::call_async` and others | request-response (callback style) | — | via the closure |
| **Async Sequenced Call** | `async_call::call_async_sequenced` | request-response (FIFO) | ✅ (FIFO within one `(app, api)` pair) | via the closure |

**How to choose**:

- you need a response and the current thread may block → **Call**
- you need a response but **do not want to block** → **Async Call**
- you do not need a response and can tolerate reordering → **Notify** (the fastest)
- you do not need a response but require ordering → **Sequenced Notify**

**The synchronous and asynchronous families have opposite handle ownership**:

| Family | Functions | Owner of the returned handle | How it is released |
|------|------|:----------------:|----------|
| synchronous | `call` / `call_by_uid` / `call_by_p2p_name` | **the caller** | the caller `Drop`s it explicitly |
| asynchronous | `call_async` / ... | **the framework** | released by the framework **immediately** after the callback returns |

**An async-family handle may only be used inside the closure body**. Using it after the closure returns is a use-after-free. Rust's safe wrapper already prevents this misuse at the type-system level, through `borrowed` semantics and `Vec<u8>` return values.

#### 3.2.5 The callback contract

Registered callbacks run on **native worker threads**. Four hard rules:

1. **Do not block.** A long-running callback occupies one thread of the native thread pool. A callback should only "read in + enqueue + return".
2. **Do not call any blocking LingoFuse function** (`framework::call`, `AppHandle::local_call`, `framework::prepare_done`, `framework::shutdown`). That deadlocks the native scheduler. When you need to issue a remote call, post the request to a separate thread, or use an **async call** (the async family may be issued from inside a callback).
3. **Do not panic.** The Rust binding isolates panics at the FFI boundary with `catch_unwind`, but a caught panic still aborts the current callback and the caller receives an empty response. Returning an error payload is preferable.
4. **Do not touch the UI.** Callbacks do not run on the main thread. To update the UI, post the result to your application's own thread-safe queue.

### 3.3 API details

#### 3.3.1 The `data_handle` module

```rust
use lingofuse::data_handle::{DataHandle, Scalar};

// construction
let mut h = DataHandle::new("api_name")?;              // auto-recycled
let mut p = DataHandle::create_permanent("template")?; // permanent

// byte I/O
h.write_bytes(&[1, 2, 3])?;
let bytes = h.read_bytes(3)?;                    // partial read; returns what was actually read
let bytes = h.read_bytes_exact(3)?;              // exact read; a short read is an error
let opt = h.try_read_bytes(3)?;                  // non-throwing; a short read returns None
let all = h.read_all_bytes()?;                   // read everything remaining

// scalar I/O (little-endian)
h.write(42i32)?;                                  // any type implementing Scalar
let n: i32 = h.read()?;
// supported: i8/u8/i16/u16/i32/u32/i64/u64/f32/f64

// string I/O (NUL-terminated UTF-8)
h.write_string("hello")?;
let s = h.read_string()?;

// cursor and size
let pos = h.position()?;
h.set_position(0)?;
let sz = h.size()?;
h.set_size(100)?;

// read the sender's identity ("side data"; valid only on the callback's input handle)
let uid  = h.p2p_uid()?;     // Uid; a non-input handle returns Uid::NULL
let name = h.p2p_name()?;    // String; a non-input handle returns an empty string

// explicit release (usually unnecessary: Drop calls it automatically)
h.dispose();
```

**The contract of `p2p_uid()` / `p2p_name()`**:

- these two methods read **the side data the sender wrote automatically when sending the request**, not a property of the handle itself
- they are **valid only on the callback's `input` handle**; calling them on an `output` handle or a self-created handle returns `Uid::NULL` / an empty string (the DLL logs a warning but does not error)
- the underlying pointer is valid for about 5 seconds; the wrapper **copies it immediately**, so the returned value may be kept as long as you like

#### 3.3.2 The `io` module

```rust
use lingofuse::io;

// JSON serialization / deserialization (no handle)
let text = io::dumps_json(&my_value)?;
let value: MyType = io::loads_json(&text)?;

// write into a handle (a NUL terminator is appended automatically)
io::write_json(&mut h, &request)?;

// read from a handle
let response: MyResponse = io::read_json(&mut h)?;
let opt = io::try_read_json::<MyResponse>(&mut h)?;  // non-throwing

// strings
io::write_string(&mut h, "hello")?;
let s = io::read_string(&mut h)?;

// bytes
io::write_string_bytes(&mut h, &payload)?;
let bytes = io::read_string_bytes(&mut h)?;   // reads up to the first NUL
let bytes = io::read_all_bytes(&mut h)?;      // reads everything
let bytes = io::peek_string_bytes(&mut h)?;   // does not move the cursor

// three-state read
match io::read_json_or_bytes(&mut h)? {
    io::JsonOrBytes::Json(v) => { /* valid JSON */ }
    io::JsonOrBytes::Bytes(b) => { /* raw bytes */ }
    io::JsonOrBytes::Empty => { /* empty */ }
}
```

#### 3.3.3 The `app_handle` module

```rust
use lingofuse::app_handle::AppHandle;

let app = AppHandle::new("MyApp", "description")?;

// register a Call API (request-response)
app.register_call("add", "addition", |input, output| {
    // input / output are borrowed DataHandles
    // do not dispose, do not block, do not issue synchronous remote calls
    if let Ok(args) = io::read_json::<AddArgs>(input) {
        let _ = io::write_json(output, &AddResult { sum: args.a + args.b });
    }
})?;

// register a Notify API (one-way)
app.register_notify("log", "logging", |input| {
    // no output
})?;

// unregister
let removed = app.unregister("add")?;   // bool

// in-process call (does not go over the network)
let resp = app.local_call(&req)?;
app.local_notify(&req)?;

// bind to an idle client
let count = app.bind()?;                // i32

// explicit release
app.dispose();
```

#### 3.3.4 The `framework` module

```rust
use lingofuse::framework;
use lingofuse::uid::Uid;

// --- network preparation ---
framework::reset_prepare();
framework::prepare_service("ipc:my_node", "ipc:my_node")?;
framework::prepare_client("ipc:my_node", Some(&app))?;
framework::prepare_done()?;

// --- App-name addressing ---
let resp = framework::call("RemoteApp", &param, 3000)?;          // never returns null
let opt = framework::try_call("RemoteApp", &param, 3000)?;       // an empty response gives None
framework::notify("RemoteApp", &param)?;
framework::sequenced_notify("RemoteApp", &param)?;

// --- UID addressing ---
let uid: Uid = /* obtained from somewhere */;
let resp = framework::call_by_uid(uid, &param, 3000)?;
let opt = framework::try_call_by_uid(uid, &param, 3000)?;
framework::notify_by_uid(uid, &param)?;
framework::sequenced_notify_by_uid(uid, &param)?;

// --- P2PName addressing ---
let resp = framework::call_by_p2p_name("worker_group", &param, 3000)?;
let opt = framework::try_call_by_p2p_name("worker_group", &param, 3000)?;
framework::notify_by_p2p_name("worker_group", &param)?;
framework::sequenced_notify_by_p2p_name("worker_group", &param)?;

// --- runtime options ---
framework::set_option("Overlap_Connection", "True")?;
let quiet = framework::get_option("Quiet")?;               // String
// or use the typed interface (see §3.3.8)

// --- application names ---
let unique = framework::generate_app_name()?;   // requires prepare_done to have run
let name = framework::get_app_name(&app)?;

// --- health checks (with about a 3-second cache delay) ---
framework::check_main_thread()?;
framework::check_app("RemoteApp")?;
framework::check_api("RemoteApp", "add")?;
framework::check_uid(uid)?;
framework::check_uid_api(uid, "add")?;
framework::check_p2p_name("worker_group")?;
framework::check_p2p_name_api("worker_group", "add")?;

// --- shutdown ---
framework::exit_main_thread();
framework::shutdown();
```

#### 3.3.5 The `network_events` module

```rust
use lingofuse::network_events;

network_events::set_network_event(
    Some(Box::new(|addr| println!("[+] connected: {}", addr))),
    Some(Box::new(|addr| println!("[-] disconnected: {}", addr))),
)?;

let installed = network_events::is_network_event_installed();

network_events::clear_network_event()?;
```

**Semantics**:

- **Connect** fires when a client first receives the server's API information broadcast, **not** on a TCP handshake
- **Disconnect** fires when the physical link drops
- **Automatic reconnection** fires Connect again, but does **not** fire Disconnect a second time

#### 3.3.7 The `uid` module

`Uid` is a safe newtype for the 32-byte P2P session identifier.

```rust
use lingofuse::uid::Uid;

// build from hex (either case accepted; the 0x prefix is optional)
let uid = Uid::from_hex("0123456789abcdef0123456789abcdef\
                         0123456789abcdef0123456789abcdef")?;

// build from a byte array / slice
let uid = Uid::from_bytes([0u8; 32]);
let uid = Uid::from_slice(&bytes)?;   // the length must be exactly 32

// checks
assert!(Uid::NULL.is_null());
assert_eq!(uid.to_bytes().len(), 32);

// display
println!("{}", uid.to_hex());         // 64 lower-case hex characters
println!("{:?}", uid);                // short form: Uid(01234567..89abcdef)
```

**Traits**: `Copy` / `Eq` / `Hash` / `Default`; it can be used as a `HashMap` key.

#### 3.3.8 The `options` module

`options` provides typed option getters/setters that avoid string spelling mistakes.

```rust
use lingofuse::options;

// boolean options
options::set_quiet(true)?;
assert!(options::get_quiet()?);

options::set_overlap_connection(true)?;
options::set_wait_connection_ready_ok(false)?;
options::set_show_thread_id(false)?;
options::set_console_output(true)?;

// integer options
options::set_wait_connection_timeout(10_000)?;
options::set_fixed_sequenced_time(20_000)?;
options::set_data_handle_idle_timeout(600_000)?;
options::set_data_handle_pool_scan_interval(5_000)?;
options::set_ipc_serv_thread_count(4)?;
options::set_ipc_serv_max_queue_length(2048)?;
options::set_ipc_serv_max_msg_size(1_048_576)?;
options::set_no_reponse_cmd_null_flush_threshold(5_000)?;

// string options
options::set_p2p_name("worker_group")?;
assert_eq!(options::get_p2p_name()?, "worker_group");

// the underlying primitives (any key)
options::set_bool("Quiet", true)?;
options::set_u64("Wait_Connection_Timeout", 30_000)?;
options::set_string("password", "my_secret")?;
let raw = options::get_string("SomeOption")?;
```

**Fallback for unknown options**: `get_bool` returns `false`; `get_u64` / `get_i64` return `0`; `get_string` returns an empty string.

**Write-only options**: `debug` is write-only; `get_debug()` returns a placeholder string.

#### 3.3.9 The `p2p` module

Process-level P2P registration, independent of any App. These APIs are reachable only by UID / P2PName addressing, **not** by app-name addressing.

```rust
use lingofuse::{io, p2p};
use lingofuse::data_handle::DataHandle;

// register a process-level Call API
p2p::register_p2p_call(
    "whoami",
    "echo caller identity",
    |input: &mut DataHandle, output: &mut DataHandle| {
        // read the sender's identity ("side data"; valid only on the input handle)
        let uid  = input.p2p_uid().unwrap_or_default();
        let name = input.p2p_name().unwrap_or_default();

        let payload = serde_json::json!({
            "uid_hex":  uid.to_hex(),
            "p2p_name": name,
        });
        let _ = io::write_json(output, &payload);
    },
)?;

// register a process-level Notify API
p2p::register_p2p_notify("p2p_log", "p2p log", |input| {
    let _ = io::read_string(input);
})?;

// unregister
let removed = p2p::unregister_p2p("whoami")?;   // bool
```

**The P2P namespace and the App namespace are independent**: an API of the same name exists in both namespaces without interfering.

**Context leak**: each registration leaks a small context object (a few dozen bytes), structurally the same as `app_handle`. The reason is in §7.1.

#### 3.3.10 The `async_call` module

The modern async call API. Every addressing mode has **callback-style** and **blocking-style** entries.

**Callback style**:

```rust
use lingofuse::async_call;
use lingofuse::data_handle::DataHandle;

let mut req = DataHandle::new("add")?;
// ... fill req ...

// App-name addressing
async_call::call_async("Calculator", &req, move |result| {
    match result {
        Ok(mut resp) => { /* use resp; it is valid only inside the closure */ }
        Err(e)        => eprintln!("async call failed: {}", e),
    }
})?;

// sequenced async (FIFO guaranteed)
async_call::call_async_sequenced("Calculator", &req, move |result| { /* ... */ })?;

// UID addressing
async_call::call_async_by_uid(uid, &req, move |result| { /* ... */ })?;

// P2PName addressing
async_call::call_async_by_p2p_name("worker_group", &req, move |result| { /* ... */ })?;
```

**Callback signature**: `FnOnce(Result<DataHandle, Error>) + Send + 'static` — structurally the same as a `std::thread::spawn` closure.

**The `DataHandle` inside the closure is borrowed**: it is valid only inside the closure body. When you need to keep the data, **read and copy it out** inside the closure:

```rust
async_call::call_async("Calculator", &req, move |result| {
    if let Ok(mut resp) = result {
        let value: MyResult = io::read_json(&mut resp)?;   // copy into a type visible outside the closure
        my_channel.send(value);
    }
})?;
```

**Blocking style**:

```rust
use std::time::Duration;

let bytes = async_call::call_async_wait(
    "Calculator",
    &req,
    Some(Duration::from_secs(5)),   // None = wait indefinitely
)?;

// bytes is a Vec<u8> holding the response payload directly (no trailing NUL)
let text = String::from_utf8_lossy(&bytes);
let value: MyResult = io::loads_json(&text)?;
```

**`call_async_wait` returns `Vec<u8>` rather than a `DataHandle`** — that is **a deliberate contract**. A handle delivered by the async family belongs to the framework and is released the moment the callback returns; wrapping it as an owning `DataHandle` and sending it across the callback boundary would cause a use-after-free. The only safe choices are "copy the bytes inside the callback" or "let the caller supply a deserialization target"; this binding chooses the former.

**Error paths**: when the dispatch fails (e.g. the framework is not started), the callback fires `Err` **synchronously** on **the caller's thread**, and the entry point itself also returns `Err`. That gives the caller one uniform error path — `?` for synchronous errors, `match` inside the closure for asynchronous ones.

**Timeouts**: the blocking `timeout` is implemented **purely on the Rust side** (`mpsc::recv_timeout`); on expiry it returns `Err(ErrorCode::Timeout)`. The native request **is not** cancelled.

### 3.5 Error handling

Every error is a `lingofuse::error::Error` carrying an `ErrorCode` classification tag.

```rust
use lingofuse::error::ErrorCode;

match framework::try_call("App", &param, 3000) {
    Ok(Some(resp)) => { /* success; resp is non-empty */ }
    Ok(None) => { /* timeout or unreachable target */ }
    Err(e) if e.code() == ErrorCode::Timeout => { /* special handling for a timeout */ }
    Err(e) => eprintln!("fatal error: {}", e),
}
```

**Error chains**: `Error::source()` returns the underlying error. The `anyhow` / `eyre` ecosystem can unwrap it directly.

**Error handling for async calls**:

```rust
// a synchronous dispatch failure propagates through ?
async_call::call_async("App", &req, move |result| {
    // an asynchronous transport failure is handled with match
    match result {
        Ok(mut resp) => { /* ... */ }
        Err(e)        => eprintln!("async call failed: {}", e),
    }
})?;
```

### 4.3 Why some tests are `#[ignore]`

**The root cause**: process-level native state (framework preparation / shutdown, network events, status posting, the option store, the P2P registry) can only be **accessed serially**. The Rust test harness runs tests concurrently by default, which conflicts.

**An example of a dangerous combination**:

- thread A calls `LF_Shutdown` (clears callbacks + stops the worker threads)
- thread B calls `LF_Set_Network_Event` (re-installs the callback pointers)

The race leaves the callback pointers and the worker-thread state held by the native layer inconsistent → later calls crash (`STATUS_ACCESS_VIOLATION`).

`#[ignore]` is the standard isolation mechanism — it changes nothing in the production code, only the test run strategy. Every test touching process-level native state is run with `--test-threads=1` to force serial execution.

### 4.4 Telling whether a test really ran

**The integration-test trap**: when the native library is missing, a test prints `[SKIP]` and returns `ok`. **`ok` does not mean it really ran.**

**How to tell**:

```bash
# add --nocapture so [SKIP] reaches the terminal
cargo test --test addressing_e2e -- --nocapture 2>&1 | grep SKIP

# no output → the native library loaded and the tests really ran ✅
# output [SKIP] → the native library was not found and the tests were skipped ⚠️
```

Or use `test.ps1 -NoCapture` and let the script handle it.

### 4.6 The validation principles shared with the other bindings

The Rust binding's test layering follows the same principles as the C++ / Python / Pascal bindings:

1. **unit tests are parallel-safe** — pure logic and stateless operations
2. **`#[ignore]` isolates process-level state** — anything touching the framework lifecycle, global options or global registries
3. **end-to-end integration** — the full call chain, split into files by area of concern
4. **`[SKIP]` when native is missing** — so CI still passes in environments without the native library

When doing cross-language regression, C++'s `test_lingofuse` and Rust's `cargo test` should observe the same wire byte sequences. Appendix C.2 gives the concrete byte-level comparison.

### 4.7 Diagnosing test failures

| Symptom | Cause | Fix |
|------|------|------|
| `cargo check --lib` warns | the code fails lint | add `#[allow]` as suggested, or fix it |
| `LibraryNotFound` | the native library is not on the search path | put it next to the executable or add it to PATH |
| `SymbolMissing { symbol: "LF_xxx" }` | the native library version does not match | check that all 59 symbols are present |
| a crash in `LF_Set_Network_Event` | tests concurrently touch native global state | add `--test-threads=1` |
| an end-to-end test stuck in the retry loop | the mesh broadcast has not arrived | increase the retry count or switch to `Wait_Connection_ReadyOk=True` |
| `STATUS_ACCESS_VIOLATION` (`0xc0000005`) | a test panicked and Drop ordering then released a handle before `exit_main_thread` | fix the root cause of the panic; do not suppress assertions |
| an async test reporting `trailing characters` | the trailing `\0` of the result handle was not stripped | use `read_string` rather than `read_all_bytes` (fixed in v0.3.0) |
| `local_call_roundtrip` fails | the callback type does not match | check the closure signature |

## Chapter 7 Known limitations and best practices

### 7.1 Known limitations

#### 7.1.1 `AppHandle` does not implement `Send` / `Sync`

The binding deliberately confines handle ownership to a single thread. Callbacks still run on native worker threads, and the closures must satisfy `Fn + Send + Sync`.

**Impact**: you cannot put an `AppHandle` inside `Arc<Mutex<>>` and share it across threads. If you need that, concentrate the registration logic in one thread and have the others post requests through a `channel`.

#### 7.1.2 Callback context leak

**Every registered API** (whether App-level or P2P-level) leaks a small context object (a few dozen bytes) until the process exits.

**The trade-off**: the native library may invoke a callback at any time (including concurrently with unregistering), so reclaiming it would cause a use-after-free. The cost is bounded.

**Impact**: do not register / unregister APIs in a tight loop. Registering once and using it long-term is the designed scenario.

#### 7.1.3 Single-process end-to-end tests

In `tests/framework_e2e.rs` / `tests/identity_e2e.rs` / `tests/addressing_e2e.rs` / `tests/async_e2e.rs` the server and the caller are in the same process, so they take the mesh's **local-first routing** path (P2PName excepted).

**Impact**: the full call chain is validated, but no TCP / cross-process IPC hop is. Cross-process validation needs two independent OS processes.

#### 7.1.4 The status queue's ABI limitation

The native ABI cannot distinguish "an empty queue" from "an empty message": both produce an empty string.

**Fix**: call `get_status_count()` first.

#### 7.1.5 The pointer lifetime of `generate_app_name` / `get_option` / the identity accessors

A native pointer stays valid for only about 5 seconds. The Rust binding **copies it immediately** into a `String` / `Uid`, so the returned value may be kept indefinitely.

**Impact**: if you use the `sys` layer directly, you must handle this yourself.

#### 7.1.6 No CI coverage

LingoFuse's automated CI covers only the C++ part. The Rust tests must be run locally.

#### 7.1.7 Platform limitations

- big-endian architectures are untested (the protocol specifies little-endian)
- 32-bit Windows is not covered by the Rust tests
- ports to edge platforms such as aarch64 / loongarch64 / RISC-V are in progress

#### 7.1.8 `call_async_wait` returns `Vec<u8>` rather than `DataHandle`

**That is a deliberate contract, not a defect.**

The result handle delivered by the async family belongs to **the framework** and is released the instant the callback returns. Wrapping it as an owning `DataHandle` and sending it across the callback boundary would cause a use-after-free (read-after-free). The only safe choices are:

1. copy the bytes inside the callback (this implementation)
2. let the caller supply a deserialization target

This binding chooses option 1. After receiving the `Vec<u8>`, the caller can decode it into a concrete type with `io::loads_json`.

#### 7.1.9 The behaviour of calling with an empty UID is undefined

The C ABI documentation says a null UID is "a legal argument that simply matches no client". But the actual wire behaviour is not part of the stable contract: the dispatcher may return an empty response, a lookup error, or a size=0 handle, depending on the routing-table state.

The Rust binding makes **no** assertion about the result of a call with an empty UID. The **query APIs** (`check_uid(Uid::NULL)` returns `false`) have a clear contract and are therefore still guaranteed.

#### 7.1.10 The `debug` option needs the framework running

`debug` is an option that "executes a command on write" rather than plain string storage. Some commands (`RegInfo`, `service`, `tunnel`) depend on the simulated main thread running. **Calling it before the framework starts blocks.**

The Rust binding's `options` module provides only setter / getter interfaces and adds no extra protection; the caller must ensure the timing.

#### 7.1.11 Options are not reset across `LF_Shutdown`

`LF_Shutdown` cleans up the network state, the App pool and the handle pool, but **does not reset the option store**. Option values persist across shutdown.

**Meaning**: when the application restarts the framework it should re-apply the configuration, rather than relying on "shutdown restores the defaults".

#### 7.1.12 No timeout and no cancellation for async calls

The C ABI's async family has no timeout parameter and no cancel handle. The callback-style entry therefore has no timeout either; the blocking entry's `timeout` is implemented **purely on the Rust side** (`mpsc::recv_timeout`), returning `Err(Timeout)` and abandoning the callback when it expires, but the native request **is not** cancelled.

If a caller needs a hard timeout, it should track the outstanding requests at a higher layer and give up after the configured time.

### 7.2 Best practices

#### 7.2.1 Always write a retry loop

The mesh broadcast can take up to about 3 seconds to reach the local cache. Even with `Wait_Connection_ReadyOk=True`, delivery of the broadcast is not guaranteed.

```rust
use std::time::Duration;

fn call_with_retry(
    app: &str,
    req: &mut DataHandle,
) -> Result<DataHandle, lingofuse::error::Error> {
    for _ in 0..30 {
        match framework::try_call(app, req, 3000)? {
            Some(resp) => return Ok(resp),
            None => {
                req.set_position(0)?;
                std::thread::sleep(Duration::from_millis(200));
            }
        }
    }
    Err(lingofuse::error::Error::new(
        lingofuse::error::ErrorCode::Timeout,
        "target did not become reachable within 6 seconds",
    ))
}
```

The same applies to `try_call_by_uid` / `try_call_by_p2p_name`.

#### 7.2.2 Keep callbacks lightweight

A callback should only "read in + enqueue + return". Post the heavy work to a separate thread.

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();
std::thread::spawn(move || {
    for job in rx {
        // do the heavy work
    }
});
let tx_clone = tx.clone();

app.register_call("heavy", "heavy work", move |input, _output| {
    let data = io::read_string_bytes(input).unwrap_or_default();
    let _ = tx_clone.send(data);  // post only, then return immediately
})?;
```

#### 7.2.3 Define payload types with `#[derive]`

```rust
#[derive(Serialize, Deserialize, Debug, PartialEq)]
struct Request {
    #[serde(rename = "user_name")]  // align with the snake_case of the other languages
    user_name: String,
    request_id: u64,
}
```

#### 7.2.4 Prefer `try_call` over `call`

`call` returns a size=0 handle on a timeout, which is easy to misread. `try_call` returns an `Option` with clear semantics.

```rust
// ❌ easy to misread: you must also check size == 0
let resp = framework::call("App", &param, 3000)?;
if resp.size()? > 0 { /* ... */ }

// ✅ clear
match framework::try_call("App", &param, 3000)? {
    Some(mut resp) => { /* there is a response */ }
    None => { /* timeout or unreachable target */ }
}
```

#### 7.2.5 Cache templates with `create_permanent`

Use a permanent handle for request templates that must outlive the process lifecycle.

```rust
let template = DataHandle::create_permanent("my_api")?;
// release it explicitly when done
template.dispose();
```

#### 7.2.6 Use `catch_unwind` as a safety net inside callbacks

Although the binding's trampoline already isolates panics, catching them yourself aids diagnosis.

```rust
app.register_call("api", "desc", |input, output| {
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        // business logic
    }));
    match result {
        Ok(v) => { let _ = io::write_json(output, &v); }
        Err(_) => { let _ = io::write_json(output, &serde_json::json!({"error": "panic"})); }
    }
})?;
```

#### 7.2.7 Register APIs before preparing the client

```rust
// ✅ the correct order
let app = AppHandle::new("MyApp", "desc")?;
app.register_call("api1", "desc", ...)?;  // ← register first
framework::prepare_client("ipc:...", Some(&app))?;  // ← prepare afterwards
```

Reversing the order makes the mesh broadcast carry an empty API list, and the first call fails.

#### 7.2.8 Host several applications with `Overlap_Connection`

```rust
framework::set_option("Overlap_Connection", "True")?;
framework::prepare_client("ipc:addr", Some(&app1))?;
framework::prepare_client("ipc:addr", Some(&app2))?;
```

Without this option the second `prepare_client` **silently discards** the second application.

#### 7.2.9 Use the typed option API rather than strings

A misspelled string option fails silently (the native layer raises no error). The typed API catches spelling mistakes at compile time.

```rust
// ❌ a misspelling fails silently
framework::set_option("Waitt_Connection_ReadyOk", "False")?;   // ignored, no feedback

// ✅ checked at compile time
options::set_wait_connection_ready_ok(false)?;
```

#### 7.2.10 For async calls, prefer the blocking style to get a `Result`

If you do not need true "non-blocking" behaviour, `call_async_wait` gives you a clear `Err(Timeout)` semantic instead of the ambiguity of `try_call`'s `Ok(None)`.

```rust
// relatively ambiguous: a timeout and an empty response share the same None
let opt = framework::try_call("App", &req, 3000)?;

// relatively clear: a timeout is an explicit Err(Timeout)
let bytes = async_call::call_async_wait(
    "App", &req, Some(Duration::from_secs(3)),
)?;
```

The only cost of `call_async_wait` is returning `Vec<u8>` (see §7.1.8), which the caller must decode itself.

#### 7.2.11 Use `Uid` rather than a bare byte array

```rust
// ❌ hand-maintaining 32 bytes is error-prone
let mut uid_bytes = [0u8; 32];
// ...

// ✅ type-safe, with friendly Debug / Display
let uid = Uid::from_hex("...")?;
println!("calling {}", uid);
framework::call_by_uid(uid, &req, 3000)?;
```

#### 7.2.12 P2P identity is readable only on the callback's `input` handle

```rust
app.register_call("whoami", "desc", |input, output| {
    // ✅ read the sender's identity from input
    let uid = input.p2p_uid().unwrap_or_default();
    let name = input.p2p_name().unwrap_or_default();

    // ❌ do not read it from output (returns NULL / an empty string)
    // ❌ do not read it from a self-created handle (returns NULL / an empty string)
})?;
```

| network preparation | `LF_PrepareService/Client/Done` | `prepare_*` | `prepare*` | `framework::prepare_*` |
| shutdown | `LF_Shutdown` | `shutdown()` | `shutdown` | `framework::shutdown` |
| network events | `LF_Set_Network_Event` | — | `setNetworkEvent` | `network_events::set_network_event` |

### C.2 Wire protocol consistency

Every binding shares **exactly the same byte-level contract**:

- UTF-8 encoding
- literal non-ASCII (no `\uXXXX`)
- NUL terminated
- little-endian integers
- tolerant reads

**The same logical payload** round-trips between any two languages with identical bytes:

```
{"a":1}  →  7B 22 61 22 3A 31 7D 00
```

### C.3 Cross-language call examples

**A Rust server + a Python caller**

Rust:

```rust
app.register_call("echo", "echo", |input, output| {
    if let Ok(s) = io::read_json::<String>(input) {
        let _ = io::write_json(output, &s);
    }
})?;
```

Python:

```python
from lingofuse import C4
client = C4("RustApp", "ipc:my_node")
result = client.echo("hello from Python")
```

**A Python server + a Rust caller**

```rust
let mut req = DataHandle::new("compute")?;
io::write_json(&mut req, &serde_json::json!({"expression": "1+2*3"}))?;
req.set_position(0)?;
let resp = framework::try_call("PythonApp", &req, 5000)?;
```

**A Rust server + a C++ async caller**

The Rust side registers a process-level API with `p2p::register_p2p_call`; the C++ side calls it through `LF_UID_Async_Call`. Both sides share the same wire contract, with identical bytes.
